# SkillboxSearchEngine

Консольный поисковый движок по локальным текстовым документам. Приложение читает настройки и запросы из JSON, строит инвертированный индекс в отдельных потоках, вычисляет релевантность и записывает ранжированные ответы в `answers.json`.

Проект выполнен по ТЗ финальной работы курса «Разработчик на C++ с нуля». Версия приложения и формата конфигурации: `0.1`.

## Технологии и зависимости

- C++17, стандартная библиотека, `std::thread`.
- CMake 3.16 или новее, CTest.
- [nlohmann/json](https://json.nlohmann.me/) 3.11.3 для чтения и записи JSON.
- [GoogleTest](https://google.github.io/googletest/quickstart-cmake.html) 1.14.0 для модульных тестов.

Зависимости включены в `third_party`: заголовок `nlohmann/json.hpp` и архив исходников GoogleTest. CMake распаковывает локальный архив GoogleTest через `FetchContent` и проверяет SHA256. Для сборки после получения репозитория доступ к сети не нужен. IDE не обязательна; проект можно открыть в CLion как CMake-проект.

## Сборка и запуск

Команды выполняются из корня этого репозитория, где находятся `CMakeLists.txt` и `config.json`. Специальные переменные среды не требуются; компилятор, средство сборки и CMake должны быть доступны в `PATH`.

### Linux

Потребуются компилятор с поддержкой C++17, CMake и Make либо Ninja.

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure
./build/search_engine
```

### Windows: MinGW, PowerShell

Добавьте каталог `bin` установленного MinGW-w64 в `PATH`. Ниже приведён пример пути: замените его на путь своей установки.

```powershell
$env:PATH = 'D:\Down\mingw64\bin;' + $env:PATH
cmake -S . -B build -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure
.\build\search_engine.exe
```

MinGW должен включать `g++` и `mingw32-make`. Не используйте один каталог сборки для разных генераторов: для другой среды задайте новое имя после `-B`.

#### Если путь проекта содержит кириллицу

Для MinGW предпочтительно клонировать проект в короткий путь из ASCII-символов, например `C:\dev\search_engine`. При локальной проверке 2026-11-02 связка CMake и MinGW не смогла собрать проект по исходному пути с кириллицей. Это ограничение инструментов сборки; работа приложения с Unicode-путями проверяется отдельно.

Обход без переноса файлов — сопоставить свободную букву диска **родительской папке** проекта. В примере ниже `R:` должен быть свободен; сначала посмотрите существующие сопоставления командой `subst` и проверьте, что диск с такой буквой не занят. Замените путь на свою родительскую папку, содержащую `search_engine`.

```powershell
subst R: "C:\Учебные проекты"
cmake -S R:/search_engine -B R:/search_engine/build-ascii -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release
cmake --build R:/search_engine/build-ascii --parallel
ctest --test-dir R:/search_engine/build-ascii --output-on-failure
.\build-ascii\search_engine.exe
subst R: /D
```

Команда запуска выполняется из настоящей папки проекта, где находятся примеры JSON. Не сопоставляйте сам `search_engine` с корнем `R:\`: генератор Makefiles может ошибаться на завершающем разделителе корневого пути. `subst R: /D` удаляет сопоставление после работы; перед следующей сборкой или запуском CTest через сохранённый каталог `build-ascii` восстановите то же сопоставление.

### Windows: Visual Studio / MSVC

Установите Visual Studio с компонентом «Разработка классических приложений на C++» и выполняйте команды из Developer PowerShell. Пример для Visual Studio 2022:

```powershell
cmake -S . -B build-msvc -G "Visual Studio 17 2022" -A x64
cmake --build build-msvc --config Release --parallel
ctest --test-dir build-msvc -C Release --output-on-failure
.\build-msvc\Release\search_engine.exe
```

В комплекте есть четыре небольших документа и запросы. После успешного запуска откройте созданный `answers.json`. Повторный запуск перезаписывает ответы.

## Параметры командной строки

```text
search_engine [--config PATH] [--requests PATH] [--answers PATH]
              [--match all|any] [--watch] [--help]
```

| Параметр | Назначение | По умолчанию |
| --- | --- | --- |
| `--config PATH` | Файл настроек и список документов | `config.json` |
| `--requests PATH` | Файл запросов | `requests.json` |
| `--answers PATH` | Выходной файл ответов | `answers.json` |
| `--match all` | Документ должен содержать все уникальные слова запроса | Основной режим |
| `--match any` | Достаточно хотя бы одного слова запроса | Выбирается явно |
| `--watch` | Периодически перечитывать документы и запросы | Выключен |
| `--help` | Показать справку | — |

Пути трёх JSON-файлов задаются относительно текущей рабочей директории. Пути из массива `files` разрешаются относительно директории выбранного `config.json`.

```bash
./build/search_engine --config config.json --requests requests.json --answers answers.json
./build/search_engine --match any
./build/search_engine --watch
```

Без `--watch` приложение выполняет один цикл и завершает работу. В режиме наблюдения повторное обновление выполняется с интервалом `config.update_interval` секунд; остановка — `Ctrl+C`. По умолчанию интервал равен 60 секундам.

## Входные данные

Пример `config.json`:

```json
{
  "config": {
    "name": "SkillboxSearchEngine",
    "version": "0.1",
    "max_responses": 5,
    "update_interval": 60
  },
  "files": [
    "resources/file001.txt",
    "resources/file002.txt",
    "resources/file003.txt",
    "resources/file004.txt"
  ]
}
```

`max_responses` необязателен; по умолчанию возвращается не более пяти документов на запрос. `update_interval` — необязательное расширение для `--watch`. При старте выводится `Starting` и название из конфигурации.

Документы состоят из строчных латинских слов, разделённых пробельными символами. Ограничения ТЗ: не более 1000 слов в документе, длина слова до 100 символов. Для отсутствующего или нечитаемого документа выводится диагностика; обработка остальных продолжается. Его позиция сохраняется, поэтому идентификаторы следующих документов не меняются.

Пример `requests.json`:

```json
{
  "requests": [
    "milk water",
    "sugar"
  ]
}
```

ТЗ допускает до 1000 запросов, каждый — от одного до десяти слов. Повторения слова внутри запроса не увеличивают его вес.

## Поиск и формат ответа

`docid` равен позиции документа в `files`, начиная с нуля. Запросы нумеруются по порядку: `request001`, `request002`, …, `request1000`.

Поиск начинается с наиболее редкого уникального слова. В основном режиме списки документов пересекаются. Для найденного документа абсолютная релевантность равна сумме частот уникальных слов запроса. Относительная релевантность:

```text
rank(document) = absolute(document) / max(absolute всех найденных документов)
```

Индексация распределяет независимые документы между рабочими потоками. Их число ограничено количеством документов и `std::thread::hardware_concurrency()`; если сведения о доступных потоках отсутствуют, используется один рабочий поток. Для каждого документа создаётся собственный счётчик слов, а общий индекс собирается после завершения рабочих потоков. Новый поток ОС для каждого файла не требуется.

Результаты сортируются по убыванию рейтинга, при равенстве — по возрастанию `docid`. Затем применяется `max_responses`. `SearchServer::GetResultCounts()` возвращает количество совпадений по каждому запросу до применения этого ограничения.

Для документов с абсолютными релевантностями 7, 3 и 10 рейтинги равны 0.7, 0.3 и 1.0. Пример формы ответа:

```json
{
  "answers": {
    "request001": {
      "result": "true",
      "relevance": [
        { "docid": 2, "rank": 1.0 },
        { "docid": 0, "rank": 0.7 },
        { "docid": 1, "rank": 0.3 }
      ]
    },
    "request002": {
      "result": "false"
    }
  }
}
```

В JSON фактические значения `float` могут содержать дополнительные десятичные знаки. `result` записывается строкой согласно образцу ТЗ. При одном совпадении `relevance` также содержит массив из одного элемента; при отсутствии совпадений поле отсутствует.

## Ошибки и неоднозначности ТЗ

Ошибки обязательной конфигурации завершают запуск с ненулевым кодом. Для предусмотренных ТЗ случаев используются сообщения:

- `config file is missing` — файл настроек отсутствует;
- `config file is empty` — отсутствует обязательный объект `config`;
- `config.json has incorrect file version` — версия отличается от `0.1`.

В исходном документе есть противоречия. Они разрешены явно:

1. Описание и алгоритм требуют совпадения **всех** слов, но пример `TestTop5` ожидает частичные совпадения. Поэтому по умолчанию применяется AND (`--match all`), а результат этого примера воспроизводится в отдельном OR-режиме (`--match any`). Исходный `TestTop5` нельзя считать корректным тестом AND.
2. В примере `TestBasic2` запрос `cappuchino` не совпадает со словом `cappuccino` в документе; также число `water` в первом документе расходится с ожидаемым счётчиком. В тестах используются согласованные данные, а опечатки не превращаются в нечёткий поиск.
3. Образец JSON использует строки `"true"` и `"false"`, а описание не уточняет тип. Здесь выбран формат образца. Образец также показывает `relevance` для одного результата, хотя текст говорит о нескольких; сохранён массив для любого непустого ответа.
4. Время обновления упомянуто без имени поля и единиц. Для дополнительного режима `--watch` определено поле `update_interval` в секундах. Обычный запуск остаётся однократным.
5. Чек-лист требует общее число результатов, но исходная сигнатура `search` его отдельно не возвращает. Добавлен `GetResultCounts()` без изменения формы результатов `search` и выходного JSON.

## Структура проекта и проверка

```text
include/        интерфейсы ConverterJSON, InvertedIndex и SearchServer
src/            реализация классов и консольное приложение
tests/          модульные тесты GoogleTest
resources/      демонстрационные документы
third_party/    локальные зависимости и лицензии
docs/           чек-лист и инструкция сдачи
.github/        автоматическая сборка и тесты
```

39 модульных тестов GoogleTest проверяют частоты слов, замену базы, поиск AND/OR, ранжирование, лимиты, количество совпадений, JSON и обработку ошибок. Они не требуют Python. Команда запуска: `ctest --test-dir build --output-on-failure` (для MSVC дополнительно `-C Release`).

Если при конфигурации CMake найден Python 3, дополнительно регистрируется тест CTest `cli_integration`. Он запускает 13 проверок консольного приложения, включая JSON-файлы, Unicode-пути, обработку ошибок и переиндексацию в режиме `--watch`. Скрипт использует только стандартную библиотеку Python. Python не нужен для сборки приложения и модульных тестов; без него интеграционный тест пропускается при конфигурации.

Проверьте регистрацию интеграционного теста командой:

```bash
ctest --test-dir build -N -R cli_integration
```

Если тест не найден, установите Python 3 или явно укажите путь к существующему интерпретатору и повторите конфигурацию. Например, для обычного каталога сборки:

```powershell
cmake -S . -B build -DPython3_EXECUTABLE="C:/Python312/python.exe"
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Замените путь к Python реальным. Для обхода через `subst` используйте те же `-S R:/search_engine` и `-B R:/search_engine/build-ascii`, что и при первоначальной конфигурации. При наличии Python CTest содержит 40 записей: 39 модульных тестов и один интеграционный набор из 13 проверок.

Локальная проверка 2026-11-02 на Windows/MinGW завершилась успешно: чистая сборка и **40 из 40 записей CTest** за 3.65 секунды. Это 39 модульных тестов и интеграционный набор из 13 проверок. Отдельный запуск на комплектных примерах также создал `answers.json`. Среда, команды и границы проверки описаны в [протоколе проверки](docs/VALIDATION.md).
